审查基线：`da9b4f5`，版本 0.5.2。只读审查实现；未修改业务代码。以下问题由主 Agent 在临时存储或真实 DSH 宿主中复现。

## 1. [P1] 移动失败时可能同时删除两份正文

位置：`src/store.ts:185-192`。

移动先提交目标写入，再提交源范围的 forget。源事务先删除正文与历史，随后重建索引、删除 journal。后两个步骤失败时，`commit` 抛出 `COMMIT_INCOMPLETE`，但源正文已经删除。`move` 将这个异常视为源未释放，无条件删除内容匹配的目标正文，导致两边都丢失。

复现：创建用户记忆，移动到项目；仅在源范围 `rebuildIndex` 注入写入失败。移动报错后，源、目标读取都返回 `ENOENT`；恢复 `rebuildIndex` 并调用 `recoverAll` 后，两边仍返回 `ENOENT`。源残留 journal 只有 forget 信息，无法恢复正文。

调整：用可恢复的跨范围移动事务记录阶段与正文，在确认源状态之前保留目标副本。源删除已经发生时不能再删除唯一剩余副本；索引更新失败应支持恢复完成移动。增加源删除后索引失败、journal 清理失败与进程中断的故障测试。

## 2. [P1] 用户记忆读取未执行访问矩阵校验

位置：`src/runtime.ts:276-280`。

`md_memory_read` 对项目目标使用 `readTarget` 做授权校验，但用户目标直接传给 `store.read`，没有检查 `state.access.user`。用户记忆在索引、搜索和列表里隐藏后，知道文件名的 Agent 仍能读到完整正文。

复现：设置当前项目的 `crossProject[projectId] = []` 并刷新。`md_memory_list({ scope: 'user' })` 返回零条；随后读取一条已存在的用户记忆，`isError=false`，返回原正文。RC.2 与 Alpha.1 都复现。

调整：读取前刷新或验证当前权限，对未授权用户范围返回明确的权限错误。补充用户范围拒绝读取的宿主测试，以及授权撤销后的直接读取测试。

## 3. [P2] 自动召回晚于宿主组装上下文，首次请求漏掉当前问题的正文

位置：`src/runtime.ts:209-220`。

两个受支持宿主都先执行 `systemPrompt.assemble`，再触发 `agent/pre-step`。插件在后者才更新当前查询并刷新召回，已经组装好的本次模型请求不会使用新正文。因此第一步可能带上前一问题的召回；新会话第一步没有当前问题的正文。若模型一步结束回答，本轮不会获得该自动召回结果。

复现：预存标题和摘要为 `ZXQNEEDLE`、正文为 `RECALL_BODY_SENTINEL` 的记忆；创建新会话并发送 `ZXQNEEDLE`。捕获第一次真实模型调用：请求不包含正文标记；调用后插件状态的 `bodies` 已包含标记，且没有上下文错误。RC.2 与 Alpha.1 都复现。

调整：在宿主组装上下文之前更新检索查询与快照，或在支持的生命周期中重新组装本次上下文。测试应检查第一次实际模型请求里的正文，而不是只检查刷新后的内部状态。

## 4. [P2] 超限对话窗口会持续堵塞后台提炼

位置：`src/extraction.ts:69-82,116-117`。

超过 128 KiB 的窗口被直接拒绝；失败保存原检查点水位。下一轮继续包含同一条超限消息，窗口只会更大，在该消息被移出有效历史前无法推进。日志里的“process a smaller window”没有对应的自动分批机制。

复现：一个包含 45,000 个汉字的用户消息触发超限，检查点保持 `boundary=-1`。下一轮追加一条短偏好消息仍超限，检查点仍为 -1，辅助模型累计调用次数为零。

调整：按字节预算分批处理，逐批推进检查点；单条消息超限也需要明确的切分规则。对保留同一会话继续输入的情况做测试，确保后续小消息仍可提炼。

## 5. [P2] 提炼候选漏掉停用条目，撞名时连同整批提案失败

位置：`src/extraction.ts:79,99-107`。

后台提炼使用默认排除 disabled 条目的快照。模型看不到停用主题，可能新建同名条目；存储层看到文件已经存在而正确拒绝更新。提炼层还会因为快照不存在该条目，丢弃提案中的 revision/hash。一个这种冲突会结束整批操作，并保留旧检查点。

复现：保存一条 disabled 用户记忆；辅助模型的 `existingMemories` 为空。返回同名 write，即使提案带有正确 revision/hash，调度仍报告版本冲突，检查点不推进。

调整：候选去重应知道停用条目的存在与状态，并明确禁止自动重新启用；把单条被拒绝的提案与整批处理的状态分开，防止一个冲突长期堵塞其余有效提案。

## 6. [P2] 损坏项目元数据后保存设置会放宽读取权限

位置：`src/management.ts:57-68`、`src/access.ts:52-76`。

独立 DSH 审查提出此问题，主 Agent 已复现。项目的 PROJECT.md 缺失或损坏时，注册表将项目放入 invalid 列表。保存设置仅将有效项目传给 normalizeMatrix，导致损坏项目的显式授权键被当作 stale 删除。删除键后，该项目读取权限回退到默认用户范围，而原设置可能明确排除了用户记忆。

复现：初始化 alpha 项目，设置 `crossProject[alpha.id] = []`；损坏 PROJECT.md 后，仅更改 debug 并保存。返回配置从 `{alpha: []}` 变成 `{}`，stale 包含 alpha，`resolveAccess(...).user` 从 false 变成 true。

调整：区分临时不可读与确实删除的项目，保留不可读项目的显式限制；权限错误路径应保持原权限或收紧权限，不能因清理矩阵而默认放宽。
